Lodgix PMS — Database Architecture

Database Architecture

PostgreSQL schema for Lodgix PMS. 39 tables across 7 domain groups. Multi-tenant with row-level isolation on every table. Soft-delete pattern applied to all financial and reservation records. TypeORM entities map 1:1 to these definitions.

Core Architectural Rule — Tenant Isolation

Every table (except tenants itself) carries a tenantId UUID NOT NULL column with a foreign key to tenants.id. PostgreSQL Row-Level Security policies enforce this at the DB layer — not just at the ORM layer. All TypeORM queries are wrapped in a TenantAwareRepository base class that automatically appends WHERE "tenantId" = $currentTenantId. This means a bug in application code cannot leak cross-tenant data.

Soft Delete Pattern

Financial records (folios, line items, payments), reservations, and guest profiles are never hard-deleted. They carry a deletedAt TIMESTAMPTZ NULL column. All queries use a base scope of WHERE "deletedAt" IS NULL. Hard deletes are only permitted on configuration tables (room type amenities, tax rules) and only by an owner-level action. This preserves audit trails and prevents revenue reporting gaps.

UUID Strategy

All primary keys are UUID generated with gen_random_uuid() (PostgreSQL 13+). This prevents enumeration attacks, is safe for multi-tenant environments, and allows client-side ID generation for optimistic UI. The exception is AuditLog which uses BIGSERIAL for efficient append-only sequential writes.

Property Domain

Single-brand tenants have exactly one Brand record created automatically on signup. The UI hides the brand selector but the data model is identical. This means single-brand tenants can be upgraded to multi-brand without any schema migration — just add more Brand rows and update the UI flag.

Financial Domain

Financial

6 tables. Folios are the financial container for a reservation. Line items and payments never get hard-deleted. The folio transfer table creates an immutable audit chain between folios.

Critical: Immutability Rules

Line items and payments are append-only. To correct a charge, post a new line item with a negative amount (a credit). Never UPDATE or DELETE a line item or payment row. This preserves the complete financial ledger for audit and dispute purposes. The deletedAt column on line_items is used only for display suppression, never for financial calculation.

outlets— Hotel facilities that generate POS charges

▼
Why this table exists

Outlets are the named facilities that can post charges to a guest folio: Main Restaurant, Poolside Bar, Zen Spa, Laundry, etc. Each outlet has a chargeType that is automatically stamped on every line item the outlet produces — no staff member manually selects the charge type. The outlet also defines the category used for per-outlet revenue breakdowns in management reports.

user_outlets— Maps staff members to the outlets they work at ▼
How this drives automatic charge attribution

When a staff member opens the POS terminal, the system reads their user_outlets entries for the current branch. If they have one outlet: that outlet is auto-selected and its chargeType and name stamp every charge they post. If they have multiple outlets: a session-start dropdown asks which outlet they are working at today — their answer persists for the session. No bartender or waiter ever manually selects a charge type.

night_audit_log— Audit run history per branch per night
APPEND-ONLY
▼
Why this table exists

Without this table, there is no record of whether the night audit ran, what it processed, or what failed. If a room charge is missing from a guest's folio, there is no way to distinguish between "the audit ran and skipped this folio" vs "the audit never ran that night". This table creates an unambiguous, per-night audit trail. The UNIQUE (branchId, auditDate) constraint also prevents the audit from running twice on the same night.

Migration Approach
Migration Strategy ▼
RuleDetail
Never rename columnsAdd a new column with the new name, migrate data, deprecate old column, drop in a later migration. Renaming breaks TypeORM mappings silently.
Add columns as nullable firstAdding a NOT NULL column to a large table locks it. Add as nullable, backfill, then add the constraint in a separate migration.
Never change enum valuesPostgreSQL enum ALTER requires a table rewrite. Instead: add a new enum type, migrate the column, drop the old type.
Index creation is CONCURRENTAlways use CREATE INDEX CONCURRENTLY on tables with existing data. Regular index creation locks the table.
All migrations are transactionalWrap in BEGIN/COMMIT. If a migration fails mid-way, it rolls back cleanly. Exception: CONCURRENT index creation cannot run inside a transaction.
Version trackingTypeORM migrations table (migrations) tracks what's been applied per environment. Never manually edit this table.
SeedingSeed scripts run after migrations in non-production environments. Default roles, room type templates, and tax rule templates are seeded per new tenant on signup — not via migration.
Schema Changelog
Revision History— Changes applied after initial architecture draft ▼
VersionChangeReason
v1.1 rooms: Split single status enum into three columns: occupancyStatus, cleanlinessStatus, heldStatus A room can be simultaneously occupied AND dirty. The combined enum made this state unrepresentable and required double conditions on every housekeeping and availability query.
v1.1 charge_type_enum: Removed deposit, added tax Deposits are payment records (liabilities), not charges. Tax rows (VAT, service charge) need their own type so they can be filtered out of revenue calculations and summed independently for tax reporting.
v1.1 line_items: Added outletId FK → outlets.id Links each charge to its source facility. Required for per-outlet revenue breakdown in management reports. Without it, all F&B revenue is a single lump sum.
v1.1 payments: Added paymentPurpose VARCHAR(25) — payment | deposit | deposit_application Deposits received at booking are liabilities, not revenue. This field allows the system to distinguish advance deposits from regular payments, and track when a deposit is applied at check-out vs still held.
v1.1 rate_plans: Added nullable outletId FK → outlets.id Placeholder for future F&B package pricing and outlet-specific promotional rates. NULL for all current room rate plans.
v1.1 guest_profiles: Added idDocExpiryDate DATE Drives the check-in flow ID state logic: first visit (no ID on file), returning-valid (expiry in future), returning-expired (expiry in past). Without this field the UI has no way to determine which state to render without manual receptionist input.
v1.1 New table: outlets — hotel facilities that generate POS charges with chargeType and category Staff members are mapped to outlets, not charge types. The outlet's chargeType is automatically stamped on every line item posted — no bartender or waiter manually selects a charge type.
v1.1 New table: user_outlets — junction table mapping staff to their assigned outlets Enables automatic charge attribution at POS. One outlet = auto-selected. Multiple outlets = session-start dropdown. Drives the outlet name appearing in line item descriptions automatically.
v1.1 New table: night_audit_log — per-branch per-night audit run history Without this, there is no way to determine whether missing room charges are due to a failed audit or an audit that never ran. UNIQUE (branchId, auditDate) also prevents double-running the audit.
v1.2 rate_plans: Replaced single-winner priority SMALLINT with cascadeTier SMALLINT + isOverride BOOLEAN Rate rules no longer pick one winner. Cascade tiers (base → seasonal → weekend → corporate) stack additively in parent→child order — a December Saturday applies the seasonal adjustment first, then the weekend adjustment on top of that running total. Negotiated and promotional rates are true overrides that bypass the cascade and set an absolute final rate.
v1.2 rate_type_enum: Removed override as a type Manager rate overrides were never a rate_plans row conceptually — they're a separate audited action via the Manager Rate Override flow, not a plan a receptionist selects from a dropdown. Removing it avoids the type being confused with the new isOverride flag, which means something different (negotiated/promotional bypass, not a manager action).
v1.2 rate_audit_log.result: Restructured from a single ruleApplied field to a cascade[] array Each cascade step now stores its own before/after running total, so the UI can render stacked rate tags ("Seasonal +25% · Weekend +5%") instead of a single rule badge. Required because multiple tiers can be active simultaneously by design.
