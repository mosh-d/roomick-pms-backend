Frontend Architecture

Full PMS frontend structure across all roles, sections, and phases. Each module maps to REST endpoints. Click any section to explore its pages, UI components, and API calls. Base URL: https://api.yourdomain.com/v1

URL Structure & Multi-Tenancy
1
Tenant resolution — Each hotel group gets a subdomain: acme.lodgix.com. The subdomain maps to a tenantId in the DB. Every API request carries this via header X-Tenant-ID (injected automatically by the auth layer).
2
Multi-brand hierarchy — Tenant → Brand → Branch (Property). All resource endpoints are scoped: /brands/:brandId/branches/:branchId/rooms
3
Single-brand shortcut — For single-brand tenants, the brand layer is transparent. The frontend skips the brand selector. DB still stores a default brand record.
4
Context provider — A global TenantContext in Next.js stores { tenantId, brandId, branchId, user, role } and is injected into every API call.
5
Route structure — /[brand]/[branch]/[module] — dynamic Next.js segments. Guards redirect unauthenticated users to /login.

Step 2 — Hotel Structure Selection
Brand Mode Picker Critical Decision
A
Single Brand — One hotel brand, one or many branches. Simpler navigation. DB: one default Brand record created. UI skips brand selector thereafter.
B
Multi-Brand — e.g. "Marriott" with sub-brands "Courtyard", "Residence Inn". DB: multiple Brand records, each with their own Branches. UI always shows brand selector at the top level.
POST/tenants/configure-mode
Request Body
{ mode: "single_brand" | "multi_brand", groupName: string, // e.g. "Acme Hotels Group" primaryBrandName: string // first brand name }
UI Components
Radio cards: Single Brand / Multi Brand Input: Group / Hotel Name Input: Primary Brand Name Toggle: White-label subdomain

▣ System — Backend Service

Rate Resolver

The single source of truth for all rate calculations. The frontend never calculates rates. Every price shown in the UI is fetched from this endpoint. Route: /rate-resolver

ARCHITECTURE RULE
Lives exclusively in NestJS as RateResolverService. Never replicated in Next.js. Any component needing a price calls POST /rate-resolver/calculate and renders the response. The response always includes a ruleApplied field — this is what makes pricing disputes auditable.
▣
Calculate Rate
Primary endpoint — called by every UI that shows a price
▼
POST/rate-resolver/calculate
Evaluates rules in priority order: manual override → corporate → promo code → negotiated → seasonal → weekend → base rate.
Request Body
{ branchId: uuid, roomTypeId: uuid, checkIn: date, checkOut: date, guestId?: uuid, corporateAccountId?: uuid, promoCode?: string, channel: "direct"|"ota"|"walkin" }
Response
{ nightlyRate: number, totalRoomCharge: number, taxes: [{ name, rate, amount }], totalWithTax: number, ruleApplied: { type, planName, planId, adjustmentApplied }, breakdown: [{ date, rate, ruleApplied }], resolvedAt: datetime }
Called from
Reservation create form Walk-in booking form Rate override confirmation Folio room charge posting Check-in flow (confirmed rate) RMS rate comparison Guest registration card OTA booking import (rate validation)
